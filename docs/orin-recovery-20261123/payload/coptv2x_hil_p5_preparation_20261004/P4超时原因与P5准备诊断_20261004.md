本记录不覆盖 2026-10-03 的 P4 密封报告。P4 通过的是接口集成门禁，不是五组路线成功完成，更不是 P5 性能验收。

## 1. 驾驶终态与直接异常

五组均为 CARLA 游戏时间超时（278.05 s），不是 GPU 崩溃、sensor timeout 或新碰撞终态。`score_penalty=1`，RC 尚未达到 100。不能把它们混同此前的基础设施失败补零结果。

帧差按固定 50 ms 换算。这是日志协议中 source frame 索引相对当前帧的年龄；考虑第 3 节的预录缓存问题，不能把它说成已确认与同一当前世界状态一致的物理采集 AoI。平均车辆速度约 0.50–1.14 m/s。同起点历史非 HIL 路线示例可以 RC=100，平均约 2.85 m/s。这里只能证明需要排查 HIL 链路；不同历史运行不能自动构成受控因果对照。

已确认的机制：结果缓存虽只选最新合法结果，推理入口仍以 FIFO 处理上千条旧触发；推理、结果发送和 ACK 受串行传输反压影响。新结果到来时，其 source frame 已远落后于当前仿真帧，形成长时间陈旧特征与 ZOH。该现象足以使原始模型的毫秒级速度差异被链路积压淹没，但不是五组驾驶超时唯一原因已被证明的声明。

## 3. 输入语义是独立问题

现有 2225 帧缓存只覆盖 `Town05:_1:r2`。其设计用途在 capture manifest 中明确为 `integration-input-only`；正式 P5 应覆盖 85 单元 × 5 组 = 425 项。

冻结配置的 `proj_first=false`，RSU 特征处于对应节点坐标系，不能笼统说它已经按 ego 位姿预投影。融合使用当前 `pairwise_t_matrix`，缓存却未保存采集时 RSU/ego 位姿。尤其本平台 `spawn_rsu()` 每 5 帧在当前 ego 附近重新生成 RSU：不同配置驾驶轨迹分叉后，同名仿真帧的 RSU 位置、观测内容不保证相同。沿用预录 source frame/SHA，仅证明取到了同一个文件，并不证明文件是当前世界状态下的 RSU 感知结果。

因此不能通过复制索引或补齐 85 个预录缓存文件，就宣称实现了严格的在线硬件在环闭环。补采集位姿可以明确坐标来源，但单靠位姿变换不能恢复已经变化的动态交通参与者，也不能补足旧视野缺失的信息。

## 4. P5 正式输入方案需要明确

推荐：当前 CARLA 世界产生 RSU 观测，Orin 接收后保存本地缓冲、在本地执行冻结推理；ROS 仍只负责轻量触发和结果，输入流的采集/落盘/传输单列计时，不能隐藏或算成模型优化收益。对过期 RSU 特征使用源时刻位姿与当前融合位姿建立正确变换。它需要修订原先“整条路线事先存好、运行时绝不传输入”的边界，不在本轮未经确认静默实施。

若坚持整条路线完全预存，可明确把实验定义为固定录制输入回放/接口评价；不能与当前 CARLA 动态状态一致的正式闭环评价混为一谈。后续需要单独设计能保证观测与轨迹一致的协议，不能通过修改 timeout 或凭帧号相同消除问题。
